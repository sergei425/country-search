# Архитектурные решения и проектирование (`DESIGN.md`)

## 1. Отмена устаревших запросов (`AbortController`)

### Как это устроено

В `SearchController` (`src/searchController.ts`) хранится ссылка на текущий экземпляр `AbortController`. При каждом новом поисковом запросе метод `search()` выполняет следующую последовательность:

1. Вызывает `this.currentController?.abort()`, немедленно прерывая предыдущий активный HTTP-запрос.
2. Создаёт новый `AbortController` и передаёт его `signal` в `searchCountries(query, controller.signal)` (`src/searchCountries.ts`), а оттуда — в нативный `fetch(url, { signal })`.
3. При получении исключения в `catch` вызывает `classifyError(error)` (`src/errors.ts`). Если ошибка имеет тип `abort` (`error.name === 'AbortError'`), она тихо игнорируется без изменения состояния UI.

### Почему `AbortController`, а не просто булев флаг (`isLatest` / `requestId`)

Использование локального флага актуальности (например, `let ignore = false` или счётчика `requestId`) решает только проблему **состояния гонки (race condition)** в интерфейсе, но оставляет ряд системных проблем:

- **Экономия сетевых ресурсов и трафика:** `AbortController` закрывает TCP-соединение на уровне браузера. Браузер перестаёт скачивать тело ответа и парсить JSON для запроса, который пользователю уже не нужен.
- **Снижение нагрузки на API и защита от Rate Limit:** при быстром вводе текста сервер не тратит ресурсы на доотправку устаревших ответов.
- **Корректная работа цепочек асинхронных операций:** сигнал отмены пробрасывается напрямую в `fetch`, гарантируя, что ни сетевой запрос, ни последующий `response.json()` не выполнятся впустую.

## 2. Обоснование выбранной задержки `debounce`

В приложении выбрана задержка **`300 мс`** (стандартный диапазон UX для live-поиска — `250–350 мс`).

### Что произойдёт, если убрать `debounce` (`0 мс`)

- **Шквал запросов:** при вводе слова из 8 букв (например, `Germany`) приложение отправит 8 отдельных HTTP-запросов (7 из которых будут немедленно отменены).
- **Лишняя нагрузка на CPU и сеть:** постоянное создание `AbortController`, перерисовка индикатора загрузки и лишние сетевые обращения на каждый символ.
- **Риск блокировки со стороны API:** при частых запросах публичные API могут начать отвечать ошибкой `429 Too Many Requests`.

### Что произойдёт, если сильно увеличить задержку (например, `1000–2000 мс`)

- **Ощущение «тормозящего» интерфейса:** пользователь закончил печатать слово, но приложение секунду или две никак не реагирует (не появляется даже индикатор загрузки).
- **Потеря интерактивности:** нарушается эффект мгновенного автодополнения, из-за чего пользователь может подумать, что поиск сломался, и начать повторно нажимать клавиши.

Значение **300 мс** соответствует средней паузе между нажатиями клавиш при осмысленном вводе текста и обеспечивает баланс между отзывчивостью интерфейса и минимальным количеством сетевых запросов.

## 3. Алгоритмическая сложность (Big O)

### Функция `mapCountryResponse(dto)` (`src/mapCountryResponse.ts`)

- **Временная сложность: $O(L + C)$**, где:
  - $L$ — количество официальных языков страны в массиве `dto.languages`;
  - $C$ — количество валют страны в массиве `dto.currencies`.
  - Все остальные поля (`name`, `capital`, `region`, `population`, `flags`) извлекаются за константное время $O(1)$.
  - Поскольку в реальных данных число языков и валют одной страны ограничено небольшой константой (в большинстве стран $1 \le C \le 3$, $1 \le L \le 15$), на практике преобразование одного объекта выполняется за **$O(1)$**, а преобразование всего массива из $N$ стран (`rawList.map(mapCountryResponse)`) — за **$O(N)$** по времени.
- **Пространственная сложность: $O(N)$** для массива из $N$ стран (создаётся новый массив чистых доменных объектов `Country` без мутации исходного DTO).

## 4. Применение принципов чистого кода

В проекте применены следующие инженерные практики и принципы:

1. **Разделение ответственности (Single Responsibility Principle — SRP):**
   - `src/debounce.ts` (`debounce`) — отвечает исключительно за управление таймерами и отложенный вызов переданной функции, ничего не зная о сети или DOM.
   - `src/searchCountries.ts` (`searchCountries`) — изолирует работу с `fetch`, кодирование URL (`encodeURIComponent`) и проверку HTTP-статусов (`response.status === 404` и `response.ok`).
   - `src/mapCountryResponse.ts` (`mapCountryResponse`) — чистая функция-адаптер (Anti-Corruption Layer), преобразующая «сырой» внешний DTO от API в безопасную внутреннюю модель `Country` с fallback-значениями.
   - `src/errors.ts` (`HttpError`, `classifyError`) — централизованная типизация и классификация всех видов сбоев (`abort`, `timeout`, `http`, `network`).
   - `src/searchController.ts` (`SearchController`) — координирует жизненный цикл запроса, отмену гонок и управление состоянием приложения (`AppState`).

2. **Чистые функции и предсказуемость (Pure Functions & Immutability):**
   - `mapCountryResponse` и `classifyError` являются чистыми функциями: при одинаковых входных аргументах они всегда возвращают одинаковый результат, не имеют побочных эффектов и не мутируют входные данные.

3. **Явная обработка ошибок и отсутствие «магических» строк (Fail Fast & Explicit Error Handling):**
   - В `src/searchCountries.ts` явно разделена бизнес-логика пустого результата (`404 -> []`) и реальных сбоев сервера (`!response.ok -> throw new HttpError(...)`), так как нативный `fetch` не считает HTTP-ошибки исключениями.
   - В `src/errors.ts` используется строгий union-тип `AppErrorKind` (`'abort' | 'timeout' | 'http' | 'network'`), исключающий опечатки при проверке типа ошибки в UI.

4. **Слабая связанность и тестируемость (Dependency Inversion / Decoupling):**
   - `SearchController` не привязан напрямую к DOM-элементам: он принимает колбэк `onStateChange` и работает через абстракцию состояния `AppState`. Благодаря этому вся логика гонки запросов (`src/raceCondition.test.ts`) тестируется в изоляции без привязки к конкретной вёрстке.
